## 0. 你先建立的心智模型（必读）

把 Agent 的「记忆」拆成 **两条管道**，不要混成一个大 list：

```text
┌─────────────────────────────────────────────────────────┐
│  A. 真相源（Source of Truth）                            │
│     event log / 落盘文件 / 工具原文                       │
│     → 完整、可回放、可以很长                              │
└─────────────────────────────────────────────────────────┘
                         │
                         │  投影函数 project()
                         ▼
┌─────────────────────────────────────────────────────────┐
│  B. 本轮给模型看的窗口（Projection）                      │
│     近窗原文 + 旧内容摘要 +「去哪读全文」的线索            │
│     → 短、够用、可省 token                                │
└─────────────────────────────────────────────────────────┘
```

| 错误想法 | 正确想法 |
|----------|----------|
| 摘要 = 删掉历史 | 摘要 = **压缩可见部分**；原文仍在 log/文件里 |
| 投影 = 再做一个聊天 UI | 投影 = **拼进 LLM 请求的那段 messages** |
| 一次做完美摘要模型 | 先管道通，摘要策略可迭代（规则 → 小模型 → 更好模型） |

这与 Cursor「Summary + recoverable source」、DeepSeek Harness「session log 派生历史」是同一类成熟套路。

## 1. 成熟版三件套分别干什么？

| 组件 | 学生一句话 | 进模型吗？ |
|------|------------|------------|
| **近窗（recent window）** | 最近 K 个回合的**原文**消息（AI/Tool） | ✅ 原文进窗 |
| **摘要（summary）** | 被挤出近窗的更早内容，压成短文 | ✅ 摘要文本进窗（通常一条 System/Human 旁注） |
| **可回查原文（recoverable）** | 摘要里带 `run_id` / 文件路径 / event 下标等线索 | ❌ 线索进窗；**全文不进**，需要时用 `read_file`/`grep` 再拉 |

最小版（已做）只有「近窗」。CTX-1 补上后两块，并把三者**稳定地组装**起来。

## 2. 推荐端到端流程（实现流畅）

以「第 N 次 reason 调用」为例：

```text
1. 图状态里已有全量 messages（执行轨迹）
2. EventLog 持续积累（或 run 结束落盘；CTX-1 可加强「边跑边记」）
3. project_context(messages, event_log, cfg) 做：
   a. 切回合（turn segmentation）——与现在 project_messages 同类，可复用加强
   b. 分成：recent = 最后 K 回合；older = 更早回合
   c. 若 older 为空 → 只输出近窗（行为≈今天）
   d. 若 older 非空：
        - 生成/更新 rolling_summary（滚动摘要）
        - 生成 pointers（可回查线索列表）
   e. 组装发给模型的列表：
        [System]
        [可选：Summary + Pointers 合成的一条上下文消息]
        [首条用户问题]
        [近窗消息…]
        [NEXT_STEP_PROMPT]
4. bind_tools 的 LLM.invoke(组装结果)
5. 新 AI/Tool 消息写回全量 messages；摘要状态写入 state 供下一轮复用
```

**关键流畅点：** 摘要最好是 **滚动（rolling）**——每挤出近窗的那一段只摘要一次，追加进总摘要，而不是每轮把全部历史重新摘要一遍（省钱、稳）。

```text
回合:  1 2 3 4 5 6 7 8 9 …   (K=5)
近窗:          [5 6 7 8 9]
摘要:  覆盖 1–4 的压缩版 + 线索
下一轮再进 10：
近窗:            [6 7 8 9 10]
摘要:  旧摘要 ⊕ 刚被挤出的「5」的增量摘要
```

## 4. 分阶段实现（按学习顺序，勿一次做完）

每阶段都有：**学什么 / 做什么 / 如何测**。确认本计划后，建议一次只开一个阶段。

### 阶段 A — 回合切割与双桶（近窗 / 过期）【基础】

| | |
|--|--|
| **学什么** | 什么叫 turn；为何不能乱切 ToolMessage |
| **做什么** | `segment_turns(messages) -> list[Turn]`；`split_recent_older(turns, k)` |
| **产出** | `app/context/window.py`（或扩 `project.py`） |
| **测试** | 构造 8 回合假消息：近窗 5、older 3；Tool 不与 AI 拆散 |

### 阶段 B — 线索（Pointers）数据结构【可回查的「地址簿」】

| | |
|--|--|
| **学什么** | 线索 ≠ 原文；只要能再次定位 |
| **做什么** | `Pointer`：`{kind, path?, run_id?, event_index?, turn_id?, hint}`；从 older turns / tool 落盘路径生成 |
| **产出** | `app/context/pointers.py` |
| **测试** | older 含 `read_file`/`mcp_call` 长结果时，指针含 path 或 event 下标 |

### 阶段 C — 滚动摘要（先规则版，再可选 LLM）【核心但可迭代】

| | |
|--|--|
| **学什么** | rolling vs 全量重摘要；摘要必须带「未决目标/已证事实/关键路径」 |
| **做什么（C1 规则版）** | 不用 LLM：把挤出的 turn 压成固定模板几行（工具名、结果前 N 字、路径） |
| **做什么（C2 LLM 版，可后做）** | 小调用：`summarize(older_chunk, prev_summary) -> new_summary`；写入 state |
| **原则** | **不做「糊弄式一句 summary」**；规则版也要结构完整，再换 LLM |
| **测试** | 挤出一轮后 summary 变长/更新；近窗仍含原文；指针不丢 |

### 阶段 D — 组装器 `build_model_context`【接到图上】

| | |
|--|--|
| **学什么** | 投影是唯一进 LLM 的历史入口 |
| **做什么** | 组装顺序见 §2；替换 `reason` 里裸 `project_messages` |
| **测试** | 假模型图：步数 > K 时，invoke 的 history **不含**最早 tool 原文，但含 summary/pointers 文本；`read_file` 仍能读落盘/log |

### 阶段 E — 回查闭环 Demo【证明「可回查」】

| | |
|--|--|
| **学什么** | 模型根据线索再拉原文（动态发现） |
| **做什么** | 提示词一句：summary 中的 path/event 可用 `read_file`/`grep`；脚本假模型：先看 summary → read_file → 答对 |
| **测试** | 端到端假模型断言 |

### 阶段 F — 文档与评测钩子【收尾】

| | |
|--|--|
| **做什么** | knowledge 短文；records；预留 token 对比（有/无摘要）指标位 |
| **非目标** | 向量库（CE-6）；多会话跨天用户画像 |

## 5. 组装进模型时的推荐消息形态（示例）

```text

Human:  [context_projection]
```

（具体用 System 还是 Human 承载 summary，实现时选一种并固定，便于测试。）

| 风险 | 学生应对 |
|------|----------|
