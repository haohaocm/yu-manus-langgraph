# 执行方案：CA-3 Plan 节点（重点）

> 状态：✅ **S0～S5 全部完成**（2026-11-24）；后置 PLAN-CLF / PLAN-REPLAN / PLAN-PROG  
> 术语：plan（规划）、reason（思考）、replan（重规划）、LangGraph node（图节点）

---

## 1. 背景与目标

**要解决：** 当前图是 `START → reason ⇄ tools → summarize`。复杂改码任务缺少「先拆步骤再执行」的显式阶段，模型容易边想边撞。CA-3 增加 **plan 节点**，让复杂任务先产出可执行步骤，再进入现有 reason/tools 循环。

**非目标（本阶段不做 / 后置）：**

- 完备的「简单/复杂」自动分类器（可用极简规则或模型自判 MVP）  
- 多轮 **replan** 状态机（可留钩子，完整逻辑后置）  
- HITL 批计划（CA-6）  
- 与 CA-4 checkpointer 深度耦合（可并行设计字段，不强绑）
- **完备分类器 / 多轮 replan** → 待办 **PLAN-CLF** / **PLAN-REPLAN**（中高），不挡本 MVP

---

## 1b. 如何判断复杂程度？（成熟做法 vs MVP）

**不要**为分流再单独「先问一轮大模型要不要 plan」——多一次完整 chat，又慢又贵，且边界仍糊。

成熟产品常见组合（由轻到重）：

1. **启发式 / 规则（零额外 LLM）**：关键词（实现/修复/多文件/重构）、消息长度、是否点名路径、是否像闲聊；误判可接受。
2. **结构化一次输出**：plan 节点（或 reason 首轮）要求 JSON：`need_plan` + `steps`；简单则 `need_plan=false` 且 steps 空——**同一次调用**完成判定+规划，不双倍往返。
3. **小分类器 / 小模型**：用更快更便宜的模型只做 binary（simple/complex），主模型只跑复杂路径。
4. **隐式计划**：不显式 plan 节点，靠 CoT/agent 边做边调；可观测性较差。

**本仓库约定：**

- **CA-3 MVP** = 上表 **1（规则 `route_need_plan`）** + 需要时再调 plan LLM；简单任务 **0 次** plan 调用。
- **后续大开发** = 待办 **PLAN-CLF**（完备分类）+ **PLAN-REPLAN**（多轮重规划状态机）。

## 3. 已拍板：图与 state（用户确认）

你的说法 **正确**，作为 CA-3 MVP 控制流定稿：

```text
START → need_plan?（规则，无额外 LLM）
          ├─ 否 → reason ⇄ tools → summarize → END
          └─ 是 → plan → reason ⇄ tools → summarize → END
```

**State（建议字段名，实现时可别名 `planning`）：**

| 字段 | 含义 |
|------|------|
| `plan` / `planning` | 步骤列表（如 `list[str]`）或等价 markdown |
| `plan_skipped` | 是否跳过了规划 |
| `plan_step_index`（可选） | 当前关注到第几步（MVP 可先不用） |

`reason` 每轮投影里带上当前 `plan`，再进 tools 循环；最后 `summarize`。

---

## 4. 复杂度 / 粒度 / replan —— 分层结论

| 主题 | MVP（CA-3） | 后续（中高待办） |
|------|-------------|------------------|
| 简单 vs 复杂 | **规则分流** `need_plan?` | **PLAN-CLF** 完备分类器 |
| 步粒度 | prompt 约定 3～7 步、可观察结果 | 可再学自适应 |
| 重规划 | 不单开节点；reason 可改文案 | **PLAN-REPLAN** 多轮状态机 |

粒度约定：一步 ≈ 一个可观察结果；禁止过细/过粗；可点名工具类型但不锁死参数。
